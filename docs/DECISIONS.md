# DECISIONS —— 关键决定、原因与后果

本文档记录 AutoCommentReply 的关键技术决定。每条记录包含：背景/原因、后果（影响）、当前状态。

规则：如需变更某个决定，必须在本文档**追加**新记录并说明原因，不能静默修改或绕过既有决定。

记录日期：2026-08-14

## 决定 1：第一阶段仅支持 Bilibili

- **背景/原因**：项目从单一平台起步，先把“评论读取 → 树/对话链”这一条链路跑通，避免同时适配多个平台导致范围和复杂度失控。
- **后果**：MVP1 的模型、树算法、Adapter 边界都按 B 站设计；后续若加平台，需要新增对应 Adapter，模型层尽量复用。
- **状态**：已确定（MVP1 内不变更）。

## 决定 2：使用 B 站网页实际使用的评论接口，而非第三方爬虫框架

- **背景/原因**：第三方框架封装不透明、更新滞后；直接使用网页实际接口，数据字段与网页端一致，可控性更强。参考项目曾使用旧 `x/v2/reply`，当前经验证的具体端点见决定 11。
- **后果**：接口为非公开 API，可能变更或触发风控，因此必须用 `BilibiliAdapter` 隔离（见决定 6），并遵守错误与分页原则。
- **状态**：已确定。

## 决定 3：核心字段统一命名，并保留与 B 站字段的显式映射

- **背景/原因**：B 站返回的字段名（`rpid`、`mid`、`uname`、`root`、`parent`、`ctime`）语义不直观；统一为 `comment_id`、`user_id`、`username`、`content`、`root_id`、`parent_id`、`created_at`，让业务代码易读，且为将来多平台预留一致接口。
- **后果**：模型层稳定、易测试；代价是 Adapter 内必须维护一张字段映射表，接口字段变更时只改映射。
- **状态**：已确定。

## 决定 4：根据 rpid / root / parent 构建评论树与对话链

- **背景/原因**：评论是树状结构，而业务（如 AI 生成回复）需要“上下文”——被回复的是谁、这条对话从哪句开始。`root` 给出根，`parent` 给出直接父，两者结合即可重建树并提取“根到叶对话链”。参考项目 [FunnySaltyFish/bilibili_comments_crawl](https://github.com/FunnySaltyFish/bilibili_comments_crawl) 提供了从评论树提取对话链的思路。
- **后果**：所有消费方（AI、人工审核）都能拿到完整上下文；算法须处理缺父、循环等边界（见 ARCHITECTURE 3.4）。
- **状态**：已确定。

## 决定 5：用户身份依赖 mid，而不是用户名

- **背景/原因**：B 站用户名可随时修改，同名也可能存在；`mid` 是稳定唯一标识。身份判断（如“不回复作者本人”“记住某人已回复过”）必须基于 `mid`。
- **后果**：`username` 只作展示字段，任何涉及身份的判断都引用 `user_id`；模型与文档都明确此约束。
- **状态**：已确定。

## 决定 6：用 BilibiliAdapter 隔离所有非公开 API 细节

- **背景/原因**：接口路径、Cookie、响应 JSON 都是易变且不可依赖的细节；把变化收口到一个类里，业务层只面对干净模型，接口变更时只改一处。
- **后果**：Adapter 是硬边界：接口相关代码不得外泄；同时 Adapter 只做读取与规范化，不做 AI、存储、回复。
- **状态**：已确定。

## 决定 7：MVP1 只做完整评论树读取

- **背景/原因**：先解决“能不能稳定、完整地把评论读出来”这个基础问题；AI、数据库、自动回复、前端都有各自的复杂度与风险，提前实现会互相干扰，且无法验收。
- **后果**：MVP1 交付物小、可独立验收；后续里程碑按顺序推进，任何编码 Agent 都不得提前实现范围外功能（见 AGENTS.md）。
- **状态**：已确定（当前里程碑）。

## 决定 8：后续路线顺序为 SQLite 增量去重 → AI 决策与生成 → 人工审核 → 自动回复

- **背景/原因**：每一步都依赖上一步：没有去重存储，重复读取会浪费且无法增量；没有 AI 生成就没有可审核内容；没有人工审核就直接自动回复风险不可控。人工审核放在自动回复之前，保证 AI 不直接对外发言。
- **后果**：路线图清晰、依赖有序；MVP1 只须保证数据模型和 Adapter 输出便于后续接入，不需要提前实现这些功能。
- **状态**：已确定。

## 决定 9：参考项目仅作思路参考，不复制代码与范围

- **背景/原因**：开源项目（[Yotsuki2213/BiliBili_VideoRead_MCP](https://github.com/Yotsuki2213/BiliBili_VideoRead_MCP)、[FunnySaltyFish/bilibili_comments_crawl](https://github.com/FunnySaltyFish/bilibili_comments_crawl)、[xiaoyaya191/bilibili_learning_bot](https://github.com/xiaoyaya191/bilibili_learning_bot)）各自目标不同：前者偏 MCP 工具封装、中间偏评论抓取与对话链、后者偏完整 AI 交互自动化。直接照搬会把别人的范围与历史包袱带进来。
- **后果**：本仓库的里程碑、边界、验收标准始终以 docs 为准；引用时注明出处，不复用其实现细节。
- **状态**：已确定。

## 决定 10：MVP1 使用 Python 3.11+、httpx 与标准库数据模型

- **背景/原因**：评论抓取需要可靠 HTTP、可注入测试 Transport、清晰的数据模型和低门槛 CLI。Python 适合当前只读数据处理，`httpx` 可复用连接并支持离线 Mock；标准库 `dataclasses` 足以表达稳定模型，不需要引入数据库或大型框架。
- **后果**：项目使用 `uv` 管理依赖，`pytest` 做测试，`ruff` 做格式和静态检查；当前不引入 Web 框架、ORM、任务队列或 AI SDK。
- **状态**：已确定（MVP1）。

## 决定 11：当前主评论使用 WBI 游标接口，楼中楼使用独立页码接口

- **背景/原因**：2026-08-14 实测旧 `/x/v2/reply` 只能返回少量评论，不能满足完整读取；`/x/v2/reply/wbi/main` 能通过 `cursor.pagination_reply.next_offset` 连续取得主评论，`/x/v2/reply/reply` 能按根评论分页取得全部后代。
- **后果**：Adapter 实现 `/x/web-interface/nav` 的 WBI key 派生和签名；主评论按游标读取，楼中楼以唯一评论数达到 `page.count` 为正常完成依据。若在达到总数前提前空页，则标记不完整。接口变化仍只修改 `BilibiliAdapter`。
- **状态**：已确定（按 2026-08-14 实际接口；未来可在 Adapter 内替换）。

## 决定 12：孤儿、错根与循环节点单独报告，不伪造父子关系

- **背景/原因**：把缺父节点直接挂到根下会制造原始数据中不存在的直接父子关系，与 `parent_id` 语义和验收标准冲突。
- **后果**：合法节点进入 `trees`；缺父、`root_id` 不一致或循环节点保留在平面 `comments` 中，并通过 `orphan_comment_ids` 与 diagnostics 报告。出现这些关系错误时 `complete=false`。
- **状态**：已确定。

## 决定 13：MVP1 JSON 同时输出平面评论、树、对话链与完整性元数据

- **背景/原因**：平面列表便于索引，嵌套树便于检查结构，根到叶 ID 链便于后续恢复上下文；只输出其中一种会迫使消费方重复推导。非公开接口和分页还要求显式表达局部失败。
- **后果**：schema 1.0 顶层固定包含 `complete`、`video`、`stats`、`comments`、`trees`、`conversation_chains`、`orphan_comment_ids`、`duplicate_comment_ids` 和 `diagnostics`。对话链使用 ID 避免大量重复复制正文。
- **状态**：已确定。
