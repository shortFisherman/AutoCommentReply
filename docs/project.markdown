# 项目：AutoCommentReply —— 为什么做、长期意图与原则

> 本文档是项目的“总体记忆”：说明动机、长期方向与常青原则。当前实现结构见 [architecture.markdown](architecture.markdown)，未来计划见 [roadmap.markdown](roadmap.markdown)，参考项目调研见 [REFERENCE_RESEARCH.md](REFERENCE_RESEARCH.md)。

## 问题与动机

视频评论区是**有层级、有上下文**的对话，而不是一行行互不相关的消息。单独拿到一条回复，很难判断它回应的是什么、整个话题从哪句开始；而“看到一条新评论就自动回一句”既没有上下文，也无法诊断和复盘。

因此本项目把“可靠”建立在数据基础上：先完整、可诊断地读取评论，保留评论之间的关系与对话链，然后才谈得上判断、生成与回复。最终目的不是盲目刷回复，而是在可控条件下帮助读取、判断并回复视频评论——每一步都可检查、可追溯。

## 长期目标链路

```text
读取评论 → 增量去重存储 → AI 决策与生成 → 人工审核 → 自动回复
```

- 读取评论：完整拿到一条视频当前可见的评论树（MVP1 已实现）。
- 增量去重存储：避免重复抓取和重复处理，提供稳定历史。
- AI 决策与生成：基于树与对话链上下文，决定是否回复并生成草稿。
- 人工审核：AI 不得直接对外发言，草稿必须有人确认、修改或拒绝。
- 自动回复：只发送审核通过的内容，并且可限速、可幂等、可审计。

## 当前状态（简洁指针）

MVP1（只读评论树与根到叶对话链）已实现：代码可运行，离线测试覆盖主要路径，项目所有者已用根目录本地的 `comments.json` 做过真实运行与人工检查。

本地 `comments.json` 是运行产物，不是稳定 fixture；其中的视频、评论内容、用户名与数量属于私有运行证据，不进入长期文档，也不作为验收依据。具体实现事实以 [architecture.markdown](architecture.markdown) 为准。

## 常青原则

- **上下文优先**：给后续判断的不是打乱的评论列表，而是保留根到叶关系的对话链。
- **完整性诚实**：局部失败不能伪装成功。读取不完整就必须明确标记，宁可少数据，不能假数据。
- **远端读取与写入隔离**：读取逻辑不碰写接口；写入（自动回复）是未来独立阶段。
- **自动对外发言前必须有人审**：AI 生成的回复不直接发出。
- **身份以 mid/user_id 为准**：username 可改名、可重复，只作展示。
- **凭证不进仓库与日志**：Cookie 等账号凭证只能来自本机私有位置，不得写进源码、文档、日志或版本库。
- **非公开 API 变化被隔离**：B 站接口细节只允许存在于 Adapter 边界内，变化时只改一处。
- **按里程碑推进**：每个里程碑可独立验收；路线图不是实施授权。
- **参考项目只借思路**：不复制无授权代码，也不照搬其范围。
