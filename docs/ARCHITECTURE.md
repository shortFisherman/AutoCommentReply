# ARCHITECTURE —— 数据流、模型、树与对话链算法、Adapter 边界

## 1. 总体数据流

MVP1 的数据流是单向、只读的：

```text
B 站网页评论接口（当前为 x/v2/reply/wbi/main + x/v2/reply/reply）
        │
        ▼
BilibiliAdapter（登录态、构造请求、翻页、解析、错误处理）
        │
        ▼
规范化评论模型列表（核心字段统一命名）
        │
        ▼
评论树构建器（按 rpid / root / parent 建树）
        │
        ▼
评论树 + 对话链
        │
        ▼
结构化输出（JSON / 控制台，供后续里程碑消费）
```

关键原则：**业务层永远不直接接触 B 站接口细节**。接口路径、Cookie、响应 JSON 结构只存在于 `BilibiliAdapter` 内部。

## 2. 核心数据模型

每条评论规范化为统一模型，字段名与 B 站响应字段一一对应：

| 模型字段 | B 站字段 | 含义 | 说明 |
| --- | --- | --- | --- |
| `comment_id` | `rpid` | 评论唯一 ID | 在一次视频评论读取结果中用于去重、建树和定位评论 |
| `user_id` | `mid` | 用户唯一 ID | 身份判定的唯一依据 |
| `username` | `uname` | 用户名 | 仅展示，可改名，不作身份 |
| `content` | `content.message` | 评论内容 | 纯文本内容 |
| `root_id` | `root` | 根评论的 `rpid` | 按当前模型约定，根评论自身为 0 |
| `parent_id` | `parent` | 直接父评论的 `rpid` | 按当前模型约定，根评论自身为 0 |
| `created_at` | `ctime` | 评论时间 | Unix 时间戳 |

除上述核心字段外，模型可携带视频上下文（如 `video_id`，对应 B 站 BV 号或 aid），用于说明评论来自哪条视频；这不改变核心字段语义。

### 字段约定

- `comment_id` 是评论标识；至少在同一视频的一次完整读取结果中不应出现两个相同 `rpid`。若出现重复，Adapter 应记录异常并按同一评论处理。
- 根评论（主楼）：`root_id == 0` 且 `parent_id == 0`。
- 回复：`root_id` 指向它所属的根评论，`parent_id` 指向它的直接父评论（不一定是根）。
- B 站的楼中楼回复最终都挂在同一个根评论下；因此 `parent_id` 与 `root_id` 不相等时，说明中间还有一层。

## 3. 评论树与对话链算法

### 3.1 建索引

把规范化后的评论列表放入一个以 `comment_id` 为键的字典，形成 `rpid → 评论` 的索引，便于 O(1) 查找父评论。

### 3.2 构建评论树

对每条评论：

1. 若 `root_id == 0` 且 `parent_id == 0`，它是根评论，直接作为树根。
2. 否则，它的父节点是 `parent_id` 对应的评论（先从索引里查；查不到则标记为“孤儿节点”并挂到根下或单独收集，不能崩溃）。
3. 每个节点维护 `children` 列表；同一层内建议按 `created_at` 升序排列，保证输出顺序稳定。

树的结构：

```text
根评论 A (rpid=100)
├─ 回复 A1 (rpid=110, parent=100, root=100)
│   └─ 回复 A1a (rpid=111, parent=110, root=100)
└─ 回复 A2 (rpid=120, parent=100, root=100)
根评论 B (rpid=200)
└─ 回复 B1 (rpid=210, parent=200, root=200)
```

### 3.3 提取对话链

“对话链”指从根评论到某一评论之间逐级相连的路径。MVP1 需要支持两种互补的提取方式。

#### 查询某一条评论的上下文

1. 从目标评论开始。
2. 不断取 `parent_id` 指向的评论（用索引查）。
3. 直到遇到根评论（`root_id == 0`）或找不到父评论为止。
4. 把路径逆序，得到 `根 → … → 父 → 目标` 的对话链。

示例：对 `rpid=111` 的评论，对话链为 `[100, 110, 111]`（即 A → A1 → A1a）。

#### 导出全部完整对话分支

从每个根评论开始做深度优先遍历（DFS）：

1. 进入一个节点时，把它追加到当前路径。
2. 如果该节点没有子节点，它就是叶子；输出当前路径作为一条完整对话链。
3. 如果它有多个子节点，就分别递归进入每个子节点。
4. 离开节点时，把它从当前路径移除，再处理下一个分支。

以上文的树为例，应输出 `[100, 110, 111]`、`[100, 120]` 和 `[200, 210]`。这样交给后续 AI 的不是打乱顺序的评论列表，而是保留上下文的完整对话分支。

### 3.4 边界处理

- **缺父**：`parent_id` 指向的评论不在数据里（被删、被屏蔽、分页缺失）时，链在断点处结束，并把该节点和本次读取标记为“不完整”；可以继续处理其他分支，但不能把断链结果冒充完整结果。
- **循环**：理论上 B 站数据不会形成环，但算法应记录已访问的 `comment_id`，一旦重复立即停止，防止死循环。
- **空数据**：没有任何评论时，输出空树/空列表，不报错。

## 4. BilibiliAdapter 边界

`BilibiliAdapter` 是本项目隔离非公开 API 的唯一入口，职责边界如下：

### 4.1 必须做（Adapter 内部）

- 管理登录态（如 Cookie）与必要的请求头。
- 从环境变量或本机私有配置读取 Cookie；不得把凭证写进源码、文档、日志或版本库。
- 构造请求、调用 B 站评论接口（当前主评论为 `/x/v2/reply/wbi/main`，楼中楼为 `/x/v2/reply/reply`），并处理接口的分页参数。
- 解析 B 站响应 JSON，映射成第 2 节的统一模型。
- 分类处理错误（网络、HTTP 状态、登录/风控、参数错误）并重试。

### 4.2 必须不做（Adapter 外部也禁止）

- 业务层不得直接拼接口 URL、读 Cookie、解析 B 站 JSON。
- Adapter 不负责 AI 决策、数据库存储、自动回复、前端展示。
- Adapter 只读取，不执行任何写操作。

### 4.3 为什么这么做

B 站接口是非公开的，随时可能改参数、字段或增加风控。把所有依赖收进一个类后，接口变更只需要改 `BilibiliAdapter`，其余代码完全不受影响。

## 5. 分页与错误基本原则

### 5.1 分页

- 主楼（根评论）按照接口当前采用的分页方式读取（可能是页码，也可能是游标），每页处理完再取下一页。
- 每条根评论下的回复也要分页读完（楼中楼同样有分页）。
- 成功终止条件必须明确：接口返回空数据、明确表示没有下一页，或已达到接口给出的总数。
- 最大页数上限只能作为防止死循环的安全阀；一旦触发，必须停止并把结果标记为“不完整”，不能当作正常读完。
- 分页循环必须是“读完为止”，不允许只取第一页就当完成（除非数据确实只有一页）。
- MVP1 不做增量与去重，但分页逻辑应便于后续接入“上次读到的位置”。

### 5.2 错误分类与处理

- **网络错误**（超时、连接失败）：可重试，重试次数有上限，两次之间退避等待。
- **HTTP 错误**（如 403、412）：通常是登录态失效或触发风控，重试无意义，应停止并给出可读提示。
- **业务错误**（参数错误、视频不存在、评论已关闭）：直接停止，并说明原因。
- **解析错误**（字段缺失、类型不符）：记录日志并把本次结果标记为“不完整”；可以继续处理不受影响的评论，但不得静默丢弃。若缺少 `rpid`、`root`、`parent` 等关系字段，当前评论无法可靠建树，必须明确报告。

总原则：**单条失败不拖垮整体，可诊断性优先**；所有失败都应有可读日志，说明“发生了什么、在哪里、下一步怎么办”。

## 6. 后续里程碑的接口预留

MVP1 的模型与 Adapter 输出要保持稳定，方便后续按顺序接入：

- SQLite 增量去重：以 `comment_id` 为唯一键，按 `created_at` 增量抓取。
- AI 决策与生成：消费评论树与对话链作为上下文。
- 人工审核：审阅 AI 草稿，只有通过后才进入自动回复。
- 自动回复：通过 B 站回复接口提交，写操作只允许出现在这一步，且仍需通过 Adapter 隔离。

这些能力现在**不实现**，只要求现有设计不堵死它们的接入路径。
