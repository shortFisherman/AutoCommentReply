# PROJECT —— 项目做什么、不做什么、验收标准

## 1. 项目定位

AutoCommentReply 的**最终目标**是：自动读取视频评论，并在需要时（例如满足规则或通过人工审核后）自动回复评论。

最终形态的完整链路预想为：

读取评论 → 增量去重存储 → AI 决策与生成 → 人工审核 → 自动回复

但本项目**按里程碑推进**。当前只做第一个里程碑 MVP1，不一次性实现整条链路。

## 2. 当前阶段：MVP1（完整评论树读取）

**里程碑声明**：MVP1 只做一件事——通过 B 站网页实际使用的评论接口，读取一条视频的完整评论树，并输出结构化数据。

### MVP1 做什么

- 仅支持 Bilibili 平台。
- 通过 B 站网页实际使用的评论接口读取评论；当前主评论使用 `/x/v2/reply/wbi/main`，楼中楼使用 `/x/v2/reply/reply`，所有细节由 `BilibiliAdapter` 封装。
- 把每条评论规范化为统一模型，核心字段：`comment_id`/`rpid`、`user_id`/`mid`、`username`、`content`、`root_id`/`root`、`parent_id`/`parent`、`created_at`/`ctime`。
- 根据 `rpid` / `root` / `parent` 构建评论树；既支持从任意评论追溯到根评论，也支持遍历出全部“根评论 → 叶子评论”的对话链。
- 把结果以结构化形式输出（例如 JSON 文件或控制台输出），供后续里程碑消费。

### MVP1 不做什么（重要）

- 不做 AI：不调用大模型，不做“是否回复”的决策，不生成回复内容。
- 不做数据库：不写 SQLite，不做持久化与去重（这是下一个里程碑）。
- 不做自动回复：不调用任何回复接口，不修改远端数据。
- 不做前端：没有网页界面、后台管理界面或任何 GUI。
- 不支持 B 站以外的平台（YouTube、抖音、小红书等一律不在范围）。
- 不用用户名做身份判断：`username` 只是展示用，身份一律看 `mid`。
- 不复制参考项目代码：参考项目只提供思路，不进入本仓库。

## 3. 验收标准

MVP1 完成的标准（验收时逐条核对）：

1. 给定一个 B 站视频链接（或 BV 号），程序能通过 B 站网页评论接口取回评论，且代码中能明确指出所用接口。
2. 输出中每条评论都包含核心字段：`comment_id`、`user_id`、`username`、`content`、`root_id`、`parent_id`、`created_at`，字段与 B 站响应字段的映射清晰可查。
3. 评论树正确：每条回复都能通过 `parent_id` 找到直接父评论；按当前模型约定，根评论的 `root_id` 与 `parent_id` 均为 `0`。
4. 对话链正确：从任意评论出发，能沿父链追溯到根评论；也能通过深度优先遍历导出每一条“根 → 叶”分支。链上顺序正确、无循环、无重复节点。
5. 分页完整：主楼和楼中楼都有翻页逻辑；只有在接口明确没有下一页、返回空数据或已达到接口给出的总数时，才能把本次读取标记为完整。
6. 错误可诊断：网络失败、登录/风控、参数错误等被分类处理，日志能说明失败原因；局部失败可以不中断其他分支，但必须把本次结果标记为“不完整”，不能静默丢失数据后仍宣称读取成功。
7. 只读：运行过程不向 B 站发送任何回复、删除等写操作。
8. 范围克制：代码中不存在 AI、数据库、自动回复、前端相关实现（允许预留接口或注释说明，但不得实现功能）。

## 4. 边界与例外

- “完整评论树”指：主楼（根评论）以及挂在它下面的全部回复（含楼中楼）。MVP1 以“能把接口当前可返回的所有评论读完”为准，不承诺补全已删除、已屏蔽或当前账号无权看到的评论。若风控、网络或解析错误导致读取中断，输出必须明确标记为“不完整”。
- B 站非公开接口随时可能变化，因此**接口相关代码只允许存在于 `BilibiliAdapter` 内**，这是硬边界。
- 登录态（Cookie）属于 Adapter 的职责范围，MVP1 至少支持传入已登录 Cookie；具体登录方式在实现时确定，不在本项目做浏览器自动化。Cookie 是账号凭证，不能写进源码、文档、日志或提交到版本库。
